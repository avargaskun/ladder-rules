# ladder-rules (avargaskun fork)

Ruleset repository for our [`avargaskun/ladder`](https://github.com/avargaskun/ladder) fork.

Upstream keeps a single `ruleset.yaml` generated by a CI job that concatenates `rulesets/*` and
auto-merges the result **without validating it**. This fork drops that job and splits the file in
two, so *our* rules are never entangled with a sync.

## The two-file contract

| File | Owner | Rules |
|---|---|---|
| `upstream.yaml` | the upstream sync | Mirror of `everywall/ladder-rules` `ruleset.yaml`. **Do not edit by hand** — it is adopted only through reviewed pull requests, and its header comment records the upstream SHA it was taken from. |
| `custom.yaml` | us | Rules we write. The **only** place `useFlareSolverr: true` ever appears. |

ladder consumes both as a **`;`-separated list of raw URLs** in `RULESET` — there is no merge step:

```
RULESET=https://raw.githubusercontent.com/avargaskun/ladder-rules/main/upstream.yaml;https://raw.githubusercontent.com/avargaskun/ladder-rules/main/custom.yaml
```

Sources are loaded independently, so one failing does not take the other down.

## ladder fail-softs — a broken source degrades silently

`NewRulesetFromEnv` **logs** a ruleset load failure and starts anyway. There is no crash and no
non-zero exit. With two sources this means `upstream.yaml` can load while `custom.yaml` 404s,
leaving 16 upstream rules live while the canary and the only FlareSolverr rule quietly vanish.

Two consequences worth knowing before debugging a "the rules stopped working" report:

- `PrintStats()` runs **only when every source loaded**, so the
  `INFO: Loaded N rules for M domains` line is a reliable all-or-nothing signal. Its **absence**
  after a restart means degraded; a `WARN: failed to load ruleset from '<url>'` names the source.
- The expected line for the current files is **`INFO: Loaded 18 rules for 43 domains`**
  (16 + 2 rules; 41 + 2 domains).

`M` is not a unique-domain count: ladder appends each rule's `domain` unconditionally plus every
entry of its `domains` list and takes the length, so `M == rules + total domains-list entries`.

## The acceptance canary

The first rule in `custom.yaml` targets `example.com` and carries two markers,
`LADDER-INJECTION-CANARY` (an `injections` block) and `LADDER-REGEX-CANARY` (a `regexRules`
substitution). **Do not remove it.**

It exists because upstream ladder `v0.0.23` still defines `applyRules` but never calls it, so
every `injections` and `regexRules` entry is silently dropped — our fork restores the call. The
canary is the deterministic, publisher-independent proof that the restored pipeline is live: proxy
`example.com` and both markers must appear in the body. It also localises a partial ruleset
failure that the `Loaded N rules` line alone cannot — if the markers are missing but the rules
count looks plausible, `custom.yaml` is the source that did not load.

## Validation

`scripts/validate-ruleset.py` runs on every push and pull request (`.github/workflows/validate.yml`).
It asserts each file parses as YAML, is a top-level list, has only keys ladder actually reads, gives
every rule a non-empty `domain`/`domains`, and compiles every `regexRules[].match`.

Two deliberate softenings, both because upstream's live ruleset would otherwise be unmergeable:

- `tests:` is **tolerated with a warning**. Upstream ships it; ladder's Go struct has no field for
  it and `yaml.v3` discards it. Never add one.
- Unrecognised **nested** keys warn rather than fail — upstream's nytimes rule has carried a
  `ueser-agent` typo for months, which is why its Googlebot user-agent has never applied.

```bash
pip install pyyaml
python3 scripts/validate-ruleset.py upstream.yaml custom.yaml
```
